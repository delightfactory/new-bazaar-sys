# Phase 0 Technical Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Establish a reproducible React/Vite/Supabase platform with SSR-ready public routes, local database development, quality tooling, and enforceable domain boundaries.

**Architecture:** Use React Router Framework Mode on Vite for one web application that supports SSR/pre-rendered public pages and application-style authenticated routes. Supabase provides Postgres, Auth, Storage, Realtime, Queues, and Cron; Node.js provides SSR/BFF runtime and future durable workers. Database development is SQL-first with Supabase migrations and generated TypeScript types.

**Tech Stack:** Node.js 24 LTS, pnpm workspace, TypeScript strict mode, React, React Router Framework Mode, Vite, Supabase CLI and supabase-js, Tailwind CSS, shadcn/ui conventions, Lucide, Zod, React Hook Form, Dexie for later offline POS, Vitest, Testing Library, Playwright, ESLint, Prettier, GitHub Actions.

---

## Version Policy

- Use Node.js 24 LTS.
- At scaffold time install current stable compatible releases and commit `pnpm-lock.yaml`.
- Dependabot/Renovate-style updates are reviewed; major upgrades require an ADR or explicit compatibility review.
- Supabase CLI is installed as a local development dependency and invoked with `pnpm exec supabase`.
- Review the Supabase changelog before platform upgrades and before using a new Supabase product capability.
- Do not depend on `pg_graphql`; the platform uses PostgREST/supabase-js, server actions, and explicit SQL functions.

### Task 4: Establish Supabase Security Baseline

**Files:**
- Create through `supabase migration new`: security baseline migration
- Create: `supabase/tests/security_baseline.test.sql`

- [ ] **Step 1: Generate migration**

Run:

```powershell
pnpm exec supabase migration new security_baseline
```

Expected: a timestamped migration appears under `supabase/migrations`.

- [ ] **Step 2: Add private schemas and RLS guardrails**

The migration must:

- create `private` and `app_private` schemas,
- revoke public access to private schemas,
- reserve exposed `public` tables for RLS-protected API access,
- keep security-definer functions outside exposed schemas,
- document that every exposed table requires RLS before grants,
- use explicit Data API grants for `anon` or `authenticated` rather than assuming new tables are automatically exposed.

- [ ] **Step 3: Write SQL tests**

`supabase/tests/security_baseline.test.sql` must verify:

- private schemas are not usable by `anon` or `authenticated`,
- exposed business tables introduced later cannot omit RLS,
- service credentials are not needed for normal user-scoped tests.

- [ ] **Step 4: Verify**

```powershell
pnpm db:reset
pnpm db:test
```

Expected: migration and SQL tests pass.

- [ ] **Step 5: Commit**

```powershell
git add supabase/migrations supabase/tests
git commit -m "chore: add supabase security baseline"
```
